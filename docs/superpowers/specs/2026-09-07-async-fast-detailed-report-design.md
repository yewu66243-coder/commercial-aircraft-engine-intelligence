# A 档异步快速详报设计

## 背景与目标

2026 年 9 月 7 日的 GTF 验收任务运行 68.86 分钟，只形成约 7,649 个中文字符，并在结束时保留 26 项复核意见。浏览器通过一个持续近 69 分钟的 HTTP 请求等待最终结果，连接中断后显示 `Failed to fetch`，但后台仍完成了 Markdown、Word 和 PDF 导出。这说明现有流程同时存在长连接脆弱、模型调用收益偏低、正文深度不足和耗时不可控的问题。

本设计将 A 档设为工作台默认生成策略。正常模型与网络条件下，目标总耗时为 15～20 分钟，正文目标为约 12,000 个中文字符，使用 20～30 个去重后的可靠来源，形成 3～4 张分析表，并在有真实图片或可计算数据时保留或生成 2～3 张图。来源不足时不得通过重复、空泛扩写或虚构事实凑足字数。

本设计取代 `2026-09-05-report-generation-performance-design.md` 中“最多三轮全流程校订”的默认执行策略，但继续保留其中的引用真实性、正文普通字重、图题与图源居中、内部核验标记不进入正文等质量边界。

## 方案选择

采用“异步任务、并行取证、章节预算、一次全审、局部修订”的方案：

1. 浏览器提交任务后，服务立即返回任务编号，不再保持一个覆盖全部生成过程的 HTTP 长连接。
2. 后台并行执行本地论文、专利、用户资料和 Web 检索，在统一证据目录中去重、评分和分配章节。
3. 系统先确定报告提纲和章节字符预算，再根据证据按章节生成正文，避免篇幅集中在摘要或背景部分。
4. 初稿完成后只进行一次全文审查；后续最多修订 8 个高风险段落，并只复查这些段落及必要的相邻上下文。
5. 到达时间预算后导出当前最完整且已通过基础合同检查的版本，未完成事项保存在后台审计记录中。

只压缩提示词和审校轮次虽然改动较小，但无法解决浏览器长连接和任务恢复问题。固定模板与缓存方案速度更快，但会降低专题针对性，因此不作为默认方案。

## 架构与组件

### 异步任务接口

新增启动与结果读取接口，同时保留现有同步接口供旧客户端兼容：

- `POST /api/three-agent-report/start`：验证请求和模型配置，创建任务，立即返回 `202`、任务编号、进度地址和结果地址。
- `GET /api/report-progress/{task_id}`：返回当前阶段、进度、已用时间、预计剩余时间和任务状态。
- `GET /api/report-result/{task_id}`：运行中返回 `202`；成功返回完整报告与下载路径；失败返回结构化错误；任务不存在返回 `404`。
- `POST /api/three-agent-report`：继续支持旧客户端的同步调用，但新版网页不再使用该入口等待完整结果。

后台在任务完成后保存任务、进度和最终结果至少 2 小时，并设置数量上限，避免长时间运行导致内存无限增长。正在运行的任务不得仅因超过保留时长而被清理。相同任务编号的重复启动请求不得创建第二个任务。

### 时间预算控制器

每个任务建立单调时钟预算，默认总预算 20 分钟。预算按阶段分配：

| 阶段 | 目标预算 | 行为 |
| --- | ---: | --- |
| 任务规划与检索式生成 | 1 分钟 | 生成 5～6 个互补子主题 |
| 本地与 Web 并行检索 | 5 分钟 | 收集并去重 20～30 个来源 |
| 原文读取与证据编目 | 4 分钟 | 提取可引用片段、数字、图片与表格数据 |
| 分章节成稿 | 6 分钟 | 按章节预算生成约 12,000 个中文字符 |
| 全文审查与局部修订 | 3 分钟 | 一次全审，最多修订 8 个风险段落 |
| 排版与三格式导出 | 1 分钟 | 统一正文导出 Markdown、Word、PDF |

阶段未用完的预算可以留给后续阶段。达到软截止时间后停止新增检索或全文重写；接近硬截止时间时跳过低收益的可选修订并进入导出。正常情况下，三种格式导出包含在 20 分钟总预算内。已经开始的单个文件原子写入不得被强制中断；超出 20 分钟时必须记录具体超时阶段和超出秒数，不得继续新的模型调用。

### 证据与内容规划

系统建立统一证据目录，每个来源记录来源类型、标题、定位信息、可信度、相关章节、可引用片段以及数字或型号信息。来源按 URL、文件哈希和标题归一化结果去重。20～30 个来源是目标范围，不为达到数量而纳入低相关或重复来源。

提纲默认包含摘要、研究方法、技术问题、适航与监管、维修保障、供应链或市场影响、综合研判、结论与建议、参考文献。章节规划器为每个实质章节设置最低字符预算，总正文目标为 12,000 个中文字符，允许在 10,500～13,500 字符范围内根据证据密度调整。摘要、目录和参考文献不计入正文目标。

每个核心章节至少包含一个明确问题、一组证据、一段分析和一项结论。表格用于型号、时间线、适航指令、部件影响、维修能力或市场影响比较。图片只允许来自已读取文档、可追溯网页或根据有出处的数据生成；不得生成装饰性图片填充数量。

### 并行与模型调用

本地论文、专利、用户资料和 Web 检索可以并行；独立章节可以在证据分配完成后并行起草。模型调用设置并发上限，避免触发供应商限流。DeepSeek 与千问使用相同编排策略，不得在供应商失败时静默切换模型。

单次模型调用设置明确超时。网络型错误最多重试两次并使用退避；语义错误或无效 JSON 只允许一次定向纠正。某个来源或章节失败时保留其他已完成结果，不重新执行全部流程。

### 浏览器恢复

网页将当前任务编号和提交时间写入浏览器本地状态。页面刷新或重新打开时，前端先查询任务状态：

- 任务仍在运行：恢复进度展示和结果轮询。
- 任务已完成：获取最终结果、恢复报告预览和下载按钮。
- 服务短暂不可达：显示“连接暂时中断，后台任务状态待恢复”，继续有限重试，不立即宣告报告失败。
- 后端明确返回失败：显示阶段、错误类型和可操作说明。

轮询采用退避和单请求互斥，避免多个标签页每两秒持续叠加请求。最终结果成功取回后停止轮询并写入历史记录。

## 状态与错误处理

任务生命周期状态固定为 `queued`、`running`、`completed`、`failed`。报告质量状态单独使用 `passed`、`needs_review`、`draft`，因此一个任务可以正常 `completed`，同时报告质量为 `needs_review`。进度状态和最终结果使用同一任务编号。服务端记录失败阶段、异常类型和面向用户的安全错误信息，不向前端返回 API 密钥、完整堆栈或内部文件系统细节。

当部分模型调用失败但已有可用正文时，系统继续完成基础合同检查和导出，将状态标为 `needs_review`，并在后台记录缺失证据与未修订段落。只有后端明确失败且无法形成最低可用正文时，前端才显示“报告生成失败”。浏览器自身的单次网络错误不得改变后台任务状态。

## 验收标准

### 功能

- 新版网页提交任务后 2 秒内获得任务编号，主请求不等待整篇报告。
- 外部浏览器刷新、关闭后重开或出现一次网络中断，能够恢复同一任务。
- 报告完成后，网页能够恢复预览及 Markdown、Word、PDF 下载链接。
- DeepSeek 和已配置的千问都能使用同一异步流程。
- 旧同步接口保持可用。

### 性能与内容

- 使用固定 GTF 验收任务，在正常供应商响应条件下目标耗时 15～20 分钟，正常导出包含在 20 分钟预算内；仅允许已经开始的单文件原子写入完成后结束。
- 正文达到 10,500～13,500 个中文字符，目标值约 12,000；来源不足时允许低于下限，但必须记录原因。
- 使用 20～30 个去重、可定位的来源，引用编号与参考文献一致。
- 生成 3～4 张有分析价值的表格；有真实图源或可计算数据时生成 2～3 张图。
- 摘要、背景、核心分析、结论的篇幅比例符合章节预算，不出现单个核心章节明显过薄。
- 全文审查一次，局部修订不超过 8 个风险段落，不再重复整篇改写。

### 质量与回归

- 正文不出现内部核验标记或不必要的加粗主题句，图题和图源保持居中。
- Markdown、Word、PDF 使用同一最终正文，图片和表格不丢失。
- 自动测试覆盖任务启动、重复任务编号、进度轮询、完成结果、失败结果、结果过期、浏览器恢复、时间预算、章节字符预算和局部修订上限。
- 现有报告、模型选择、导出和图片测试继续通过。
- 使用外部浏览器完成一次真实任务验收，记录总耗时、正文字符数、来源数、表图数量和剩余复核项。

## 范围边界

本次不增加 A/B/C 模式切换控件，A 档直接成为默认策略；后续如需要再增加其他档位。本次不引入数据库或分布式任务队列，任务恢复范围限定为同一后台进程运行期间以及至少 2 小时的内存结果保留。服务重启后的跨进程恢复可在后续以持久化任务存储单独设计。
