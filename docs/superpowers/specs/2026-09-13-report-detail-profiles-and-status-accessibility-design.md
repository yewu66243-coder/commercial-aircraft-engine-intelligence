# 报告精细程度与状态栏可读性设计

## 背景与目标

当前 3-Agent 报告只有报告类型和模型选择，没有面向用户的生成精细程度控制。完整流程会进行较多检索、精读、写作和复核，适合正式研究，但不适合现场演示。与此同时，浅色主题已经把连接状态面板改为白色背景，面板内仍有白色或浅灰色的旧主题文字，导致任务状态几乎不可见。

本次改动增加两个明确的执行档位：

- 简洁版：正常模型与网络条件下目标 1～2 分钟，端到端目标不超过 5 分钟，产出一篇可用于展示且结构完整的情报报告。
- 精细版：目标 15～20 分钟，端到端目标不超过 30 分钟，以更多来源、更充分的分析和更完整的图表形成正式研究报告。

两个档位沿用当前正式报告格式和导出方式。DeepSeek 继续作为默认模型，千问只在用户手动选择时使用。状态面板在浅色主题下必须清晰显示连接、任务进度和模型等信息。

## 采用方案

采用“服务端配置档案 + 统一时间预算控制器”的方案。前端只提交 `report_detail=brief|detailed`，后端把它解析为完整的检索、内容、复核和时间预算。这样可以避免前端散落多组参数，也能保证 API、命令行和后续入口使用相同规则。

未采用以下方案：

- 只在前端减少来源数量：无法约束后端复核轮次、模型超时和导出预留时间，不能可靠满足 5 分钟上限。
- 建立两套独立流水线：会复制检索、写作和导出代码，后续容易出现格式和质量规则不一致。

本设计通过一个流水线和两份不可变配置实现差异。`report_type` 继续表示报告的业务结构、模板和目录规则；`report_detail` 表示执行精细程度并控制所有数量与时间上限。两者不得互相替代，发生旧长度建议与新档案冲突时以 `report_detail` 的数量预算为准。

## 用户界面与接口

### 精细程度控件

任务配置区新增独立的“报告精细程度”选择框，放在“报告类型”附近，默认选择简洁版：

- `简洁版｜预计 1–2 分钟，最长 5 分钟`
- `精细版｜预计 15–20 分钟，最长 30 分钟`

启动任务时，前端在请求体中显式发送：

```json
{
  "report_detail": "brief"
}
```

运行日志的首条配置摘要必须显示所选档位及预计时长，防止用户误以为精细版会在数分钟内完成。任务运行期间禁用该选择框，与模型、报告类型和其他本轮配置保持一致。

### 兼容性

`ThreeAgentRequestData` 增加受约束字段 `report_detail`，只接受 `brief` 或 `detailed`。新版网页总是显式传值。为保持已有 API 客户端的执行质量，未提供该字段的旧请求按 `detailed` 处理；非法值返回 422，不做猜测或静默降级。

现有 `/api/three-agent-report` 和 `/api/report-progress/{task_id}` 接口继续使用。本次不实现跨刷新任务恢复或新的持久化任务队列；此前异步任务设计仍作为独立后续工作，不扩大本次功能范围。

## 服务端配置档案

后端新增集中式 `ReportDetailProfile`，编排层只读取档案，不在各 Agent 内重复判断字符串。默认参数如下：

| 参数 | 简洁版 `brief` | 精细版 `detailed` |
| --- | ---: | ---: |
| 目标总耗时 | 60～120 秒 | 15～20 分钟 |
| 硬截止时间 | 300 秒 | 1,800 秒 |
| 导出预留 | 45 秒 | 120 秒 |
| 互补子主题 | 最多 3 个 | 最多 6 个 |
| 单次检索结果上限 | 3 | 5 |
| 去重后高可信来源目标 | 3～8 个 | 12～20 个 |
| 正文目标 | 1,500～2,500 个中文字符 | 5,000～8,000 个中文字符 |
| 全文模型审查 | 最多 1 次 | 1 次 |
| 定向修订 | 最多 1 次，仅处理硬性问题 | 最多 2 次，合计不超过 8 个高风险段落 |
| 表格目标 | 1～2 张，有合适证据时 | 2～4 张，有合适证据时 |
| 图片目标 | 0～1 张，有合适原图时 | 1～3 张，有合适原图时 |

前端现有“精读/抓取上限”仍作为用户请求值。实际单次检索上限取用户值与档案上限的较小值，因此用户可以主动减少工作量，但不能把简洁版扩张成不受控的长任务。

目标数量不是凑数要求。来源不足时不得纳入重复或低可信来源，正文不足时不得虚构或空泛扩写，图表不足时不得加入无关装饰内容。

## 流水线与时间预算

### 统一预算控制器

每个任务创建使用单调时钟的预算控制器，记录开始时间、软目标、硬截止、导出预留和当前阶段。所有网络检索、原文读取、模型调用和定向修订在开始前都必须查询剩余预算。

当剩余时间小于“导出预留 + 本次调用安全余量”时，不再启动新的远程调用，而是使用当前最佳结果进入基础校验和导出。单次调用超时取供应商默认超时与当前可用预算中的较小值，避免一次调用吃掉整个任务时间。

简洁版最迟在第 255 秒停止新增研究或模型调用并进入导出；精细版最迟在第 1,680 秒进入导出。到达硬截止时取消仍未完成的可取消远程任务。已经开始的 DOCX 原子写入或 Word 原生 PDF 转换不强制杀死进程，但必须记录超时阶段；若转换无法在剩余时间内完成，保留 Markdown 和 DOCX，并明确报告 PDF 导出条件不足或超时，不生成版式不同的替代 PDF。

### 简洁版执行策略

简洁版优先复用本地索引，最多规划 3 个互补子主题，并行查询用户选择的本地资料、论文、专利和 Web 范围。证据目录完成去重和可信度排序后，只把最相关的 3～8 个来源及必要片段发送给写作 Agent。

写作 Agent 一次性生成保持现有封面、摘要、关键词、正文结构、结论建议和参考文献格式的短报告。确定性检查始终执行，包括结构、引用编号、URL、数字与单位、内部标记和导出合同。只有存在硬性错误且预算允许时，执行一次定向修订；不进行低收益的整篇反复改写。

### 精细版执行策略

精细版最多规划 6 个互补子主题，扩大原文读取和证据目录，目标为 12～20 个去重后的高可信来源。写作按章节预算生成 5,000～8,000 个中文字符，并覆盖技术问题、适航或监管、维修保障、供应链或市场影响、综合研判和建议等与任务相关的部分。

完成初稿后进行一次全文审查，随后最多进行两次定向修订，合计不超过 8 个高风险段落。达到软目标或修改收益停滞时提前结束；不得为了用满 30 分钟而继续无效复核。

### 图表规则

证据目录为图片和表格候选记录来源文件或 URL、标题、适用章节和可追溯依据。只要存在与正文结论直接相关且可追溯的候选，报告应在相应章节纳入，而不是统一堆放在文末。

- 表格优先用于型号、时间线、部件问题、适航措施、维修能力或市场影响比较。
- 图片只允许来自已读取的本地文档、可追溯网页或基于有出处数据生成的图；不得生成装饰性图片。
- 没有合格候选时允许低于目标数量，但必须在后台审计记录中写明原因，不在正文中伪造占位图表。

## 质量状态与异常处理

两个档位使用相同的最低质量门槛和正式报告格式。时间预算只减少检索广度和重复模型复核，不跳过确定性结构、引用和导出检查。

接近截止时间时，系统选择结构完整、引用可定位且问题最少的已生成快照。若满足最低报告合同，则任务正常完成并按实际情况标记 `passed` 或 `needs_review`；若尚无最低可用正文，才标记为 `failed`。运行日志必须显示停止原因，例如“简洁版时间预算已到，已导出当前最佳版本”，而不是笼统显示服务器错误。

模型供应商失败时不得从 DeepSeek 静默切换到千问或反向切换。检索、单个来源或图片处理失败时保留其他已完成成果。Word 与 PDF 继续执行已经确定的同源规则：先生成 Word、更新目录和页码，再从同一个 Word 文件导出 PDF；无 Microsoft Word 时明确禁用 PDF，不使用 HTML PDF 回退。

## 状态栏可读性修复

### 根因

浅色主题在 `frontend/styles.css` 末尾把 `.websocket-panel` 背景改成了 `rgba(255, 255, 255, .98)`，但旧规则仍直接为标题和状态值设置 `#FFFFFF`，为标签设置 `#B8B8B8`。父级的 `color: var(--is-text)` 无法覆盖子元素自己的 `color`，因此白色状态值消失、浅灰标签对比度不足。

### 样式规则

在浅色主题规则之后增加限定于状态面板的显式覆盖，避免影响报告正文和其他控件：

- 标题、状态值：`#19324d`，白底对比度约 13.09:1。
- 标签和操作按钮：`#526b84`，白底对比度约 5.53:1。
- 成功、警告、失败文字需要着色时分别使用 `#176b46`、`#8a5a00`、`#b42318`，白底对比度均高于 5.9:1。
- 状态分隔线使用现有 `--is-line`；连接圆点继续使用绿、黄、红色，并保留文字状态，不能只依赖颜色表达含义。
- 按钮悬停态使用浅青背景和深青文字，保持键盘焦点轮廓可见。

同时更新 `index.html` 中样式表版本参数，确保浏览器不会继续使用修复前的缓存。桌面宽度和窄屏宽度使用同一套颜色规则。

## 测试与验收

### 自动测试

- 档案解析测试：验证两个合法值、非法值 422、旧请求默认精细版和新版网页默认简洁版。
- 预算测试：使用可控时钟验证剩余时间、导出预留、停止新增调用、单次超时上限和停止原因。
- 流水线测试：验证简洁版与精细版的子主题、来源、正文、审查和定向修订上限确实由档案控制。
- 降级测试：验证到达预算后导出当前最佳版本并标记 `needs_review`，无最低正文时才失败。
- 图表测试：有合格候选时必须纳入，无候选时不生成占位内容，并记录原因。
- 导出回归测试：验证 Markdown、Word 和 Word 派生 PDF 使用同一最终正文，PDF 失败时没有 HTML 回退。
- 前端测试：验证请求体携带 `report_detail`、运行时控件禁用、日志显示档位和预计时长。
- 样式测试：读取状态面板关键元素的计算样式，验证白底文字对比度至少 4.5:1，桌面和窄屏截图中所有状态字段可见。

### 真实验收

使用固定的 GTF 任务分别运行一次简洁版和精细版，记录总耗时、各阶段耗时、正文字符数、去重来源数、表格数、图片数和剩余复核项：

- 简洁版正常目标 1～2 分钟，端到端不得主动启动超过 5 分钟预算的新工作；报告正文目标 1,500～2,500 个中文字符，来源目标 3～8 个。
- 精细版正常目标 15～20 分钟，端到端不得主动启动超过 30 分钟预算的新工作；报告正文目标 5,000～8,000 个中文字符，来源目标 12～20 个。
- 两档报告均保持现有封面、目录、正文层级、引用、图题、表题、页眉页脚和三格式导出要求。
- DeepSeek 默认生成成功；手动切换千问后使用千问完成同一流程，任何失败均不发生静默换模。
- 打开状态面板后，Connection、Research、Task elapsed、Stage、Review round、Est. remaining、API online for、Last activity、Channel、Health checks、Responses、Current task 和 Current model 均清晰可见。

## 范围边界

本次不增加第三个精细程度档位，不改变任务模板语义，不重做报告版式，不引入数据库或分布式队列，也不承诺外部模型和网络始终达到目标耗时。系统需要通过服务端硬预算确保不再无界启动新工作，并对供应商延迟、导出超时和质量不足给出真实状态。

本设计在精细程度和时间预算方面取代 `2026-09-07-async-fast-detailed-report-design.md` 中单一 A 档的内容与来源规模；其中尚未实施的异步任务恢复能力不属于本次范围。Word/PDF 一致性继续以 `2026-09-10-word-derived-pdf-export-design.md` 为准。
