# 项目体检与指标测评

检查日期：2026-09-23。

检查对象：commercial-aircraft-engine-intelligence 当前工作区，包含已有未提交修改。检查依据为用户提供的《基于多智能体协同的商用航空发动机情报收集系统原型开发任务说明书》。本次覆盖报告主流程、模型选择、模板、摘要及全文检索、OCR、上传索引、原文核验、参考文献、导出、测评与前端下载，采用代码检查、离线回归测试和本地页面检查。没有执行十轮真实模型验收，也未进行网络渗透或硬件压力测试。

## 1 总体结论

系统已具备任务模板、多源检索、多智能体写作、报告审校、全文RAG、上传增量索引和Word/PDF导出的主要功能。当前突出不足是验收测评缺少完整样本和独立裁判，资料删除与索引清理未闭合，原文复核覆盖和大规模检索性能仍需改善。不能根据报告成功下载或规则初筛结果认定全部验收指标已满足。

任务书要求：单次深度检索及报告生成不超过20分钟；核心技术实体抽取准确率不低于90%；公开信息溯源链接准确率不低于98%；至少10轮测试且每轮均满足要求，准确率使用人工或大模型裁判评估。

## 2 本次已修复

1. 修正 `three_agent_service.py::run` 中错误的30分钟达标门槛，统一为1200秒。
2. 新增 `backend/reporting/evaluation_report.py`，每次研究报告导出后自动生成同名 `_指标测评.docx`、`_指标测评.md` 和单次JSON。JSON保留运行记录与核验结果，测评Word失败时仍尝试生成Markdown和JSON。
3. HTTP返回增加 `evaluation_report`，运行统计增加 `acceptance_assessment`；前端下载栏与历史记录提供测评报告链接。Word失败时按钮回退到Markdown，导出错误写入运行日志。
4. 区分“自动初筛达标/未达标”与“正式验收待复核”，无有效样本显示“无法计算”。不把链接可访问率当作溯源准确率，也不将名称匹配直接当作实体事实准确率。
5. 实体核验和正式报告整理移入工作线程，避免其中的同步文件读取、网络查证长期占用HTTP事件循环。

## 3 尚未完善的问题

### P1 准确率验收尚未闭合

位置：`gpt_researcher/evaluation/entity_evaluator.py::extract_entities_from_report`、`_match_entities`；`gpt_researcher/evaluation/source_evaluator.py::_check_claims_against_source`。

实体样本依赖Writer输出特定内部表格，缺表时得到零样本；标准答案比对按名称相等或包含关系判断，不核对数值、单位、适用条件。溯源评估按关键词、数字命中判断，部分支撑计0.5分，不能排除原文否定、数字属于其他对象等语义错误。

检查时历史记录共14条。最近5条的公开URL样本数全部为0，实体样本数依次为0、41、28、52、0，严格实体准确率均为空。最后一条耗时6.26分钟。这些记录证明耗时被记录，但不能证明90%和98%指标已达到。

建议：把内部实体清单作为独立结构化结果保存，避免依赖公开正文格式；使用来源原文逐条检查名称、数值、单位及语义；引入与写作分离的模型裁判或人工标注，并保留裁判版本、证据位置、逐项判断和分母。建设至少10轮固定测试任务和复核台账。当前测评报告已如实呈现初筛及待复核状态，尚未新增完整独立裁判服务。

### P1 同名资料删除可能误删摘要

位置：`gpt_researcher/document/local_library.py::delete_local_library_file`。

删除摘要记录时同时按相对路径和文件名过滤。分类目录中如果存在同名文件，删除其中一个可能把其他目录中的同名摘要记录一起移除。

建议：以规范化相对路径或稳定文档ID为主键；只在旧记录没有路径且匹配唯一时兼容文件名；增加两个目录同名文件的回归测试。

### P1 删除资料未同步清理全文向量库

位置：`gpt_researcher/document/local_library.py::delete_local_library_file`、`gpt_researcher/document/library_rag.py::search_library`。

删除接口只删除实体文件和摘要JSON，没有删除向量库documents/chunks，也没有取消对应上传任务。检索会跳过不存在的文件，降低了旧内容被召回的风险，但数据库和状态统计仍残留；删除与后台建库并发时也缺少统一协调。

建议：删除进入统一资料生命周期操作，使用文档路径或ID清理摘要、正文片段、任务记录和恢复缓存，处理建库并发并提供失败重试。禁止仅按文件名清理。

### P2 原文复核未完整利用正文索引

位置：`backend/reporting/source_grounding.py::build_source_catalog`。

PDF只读取前80页；DOCX只取段落而没有遍历表格；OCR恢复文本仅在整体未提取到文本时回退。因此全文RAG召回的后部章节、Word参数表、混合PDF扫描页，可能没有进入审校证据包。

建议：优先读取实际命中的页码/片段及相邻上下文，按页合并原生文本和OCR恢复文本；加入DOCX表格读取；记录核验覆盖页码，避免“检索找到但审校看不到”。

### P2 全库向量检索为线性扫描

位置：`gpt_researcher/document/library_rag.py::search_library`。

每次查询遍历有效文档，分批读取向量、解析正文元数据并计算相似度。目前分批读取控制了内存，但没有近似最近邻索引；片段规模继续增长时查询成本随总量增加。这里只是结构性风险，本次未测量实际全库延迟。

建议：记录查询耗时与候选量，先基于真实查询做基准；随后采用适合便携部署的向量索引与关键词混合召回，保留稳定文档ID、删除和增量更新机制。

### P2 历史测评JSON持久化不具备事务保护

位置：`three_agent_service.py::append_evaluation_record`。

当前读取整个列表、追加后直接覆盖原文件，没有跨进程锁或原子替换。多任务同时完成、进程中断、磁盘写入异常时可能丢失或损坏记录。损坏文件虽有备份逻辑，但不能保证当次结果持久化。

建议：每次运行独立保存记录，并以SQLite事务管理运行索引。新增测评报告已有单次JSON，但旧汇总JSON仍保留原实现。

### P2 失败任务与十轮验收统计仍需补齐

位置：`main.py::generate_three_agent_report`、`three_agent_service.py::run`。

中途异常会返回诊断并更新进度，但只有走到导出末尾才追加完整测评记录。失败任务可能没有进入历史统计。也尚无完整的十轮独立裁判验收汇总。

建议：任务建立时持久化运行ID、开始时间、配置；无论成功、失败或取消都更新终态，记录失败阶段；失败轮次不能从验收统计中隐藏。本次新增附件针对已经生成研究报告的任务。

### P2 参考文献补全仍存在实际缺项

位置：`backend/reporting/reference_lookup.py`、`reference_metadata.py`、`formal_report.py`。

已有本地提取、按题名联网补全、缓存与缺项提示，但最近3条记录仍各有1条著录信息不完整。代码和缓存无法保证外部数据库一定可访问或能唯一匹配到论文。

建议：增加人工确认并保存完整元数据的入口，保留来源和更新时间；同题名、译名与不同版本需校验后绑定。不能靠补造期刊、年份或页码解决。

### P2 窄屏资料列表过长

本地页面检查显示，当前较窄窗口会切换到单列布局，资料库列表使页面很长，报告区需要滚动至底部。新增测评按钮已采用两列布局并检查无挤压；现有资料列表的窄屏高度问题仍需单独优化。

建议：对窄屏资料库设定最大高度并内部滚动，必要时分页或虚拟化，避免一次渲染全部资料条目。

## 4 如何使用新增测评报告

重启后端并刷新页面。正常提交任务，研究报告导出后会继续生成指标测评附件，完成后点击报告预览上方的“指标测评”。历史记录也会保留本次测评下载地址。

指标测评包含运行编号、关联任务、完成时间、三项指标阈值、实测或规则初筛结果、复核原因、公开链接核验明细、阶段耗时与十轮验收说明。研究报告正文不会混入测评说明。

耗时口径是后端任务开始到研究报告导出完成，不包含请求传输、测评附件导出及浏览器接收时间。正式验收如严格采用“用户提交到用户获得结果”，还需补充前后端端到端计时。
